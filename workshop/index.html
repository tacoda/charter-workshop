The charter alone moves the band. That is the claim, and it is falsifiable.

Same agent, same model, same laptop, same ticket. Nothing changes but files in the repository. By 1:12 you will have a matrix that says how far that got you on a codebase you did not write, including the possibility that it got you nowhere. CLAUDE.md .claude/ .mcp.json and nothing else

The objection, first

A charter written in advance is a list of guesses. That objection is correct, and it is the strongest argument against this page. The resolution is that wrapping an existing application is not authoring in advance. The first run is the incident, so every rule you write today points at a diff you watched it produce twenty minutes earlier.

The turn, and the four places you can stand in it

A turn is one round trip: you ask, the harness gathers what the agent reads, the model decides, a tool writes. Four levers sit at four moments of that trip. Match the lever to the moment your problem happens.

Two words there are narrower than usual. A hook is not a git hook: it is a script the harness runs at a named moment, and its exit code is the verdict. A sub-agent is a second model call with its own window and its own tool grant, returning a result rather than a transcript.

The repository
0:055 minutes · I talk, you read

Three eras deep, and they disagree with each other

tarrasque runs a tabletop play session: it rolls the dice, tracks the turn order, holds the condition timers, and writes an append-only log the table can read back. It is not a toy, and it is not clean. It is the shape of a repository you would actually be handed.

2026 · domain 2023 · the god file 2021 · frozen
the three eras · the newest one is outnumbered, which is the whole problem
wherewhenwhat it looks like
tarrasque/domain/2026 Pure functions. An injected Rng. Every roll returns a Roll carrying its notation, its seed and its raw faces. Typed, tested, and outnumbered.
tarrasque/api/handlers.py2023 The /v1 god file. Each handler parses, queries, rolls and serializes inline. Calls random.randint. Reads character_id out of the request body. The dominant pattern by volume.
tarrasque/legacy/tables.py2021 Draws from the global random stream, keeps per-session state in a module level list, returns bare integers. Excluded from mypy and from ruff. Frozen; see docs/adr/0004.

The same job, twice, eleven lines apart

Both are in the repository right now, and both pass the test suite. One is eleven hundred lines of precedent. The other is one file. Code is a louder signal than any paragraph above it, which is the whole problem.

Four traps, and why each one is there

Opposed

Seeding, provenance and append-only each have a working implementation here that does the wrong thing, with no correct exemplar on the path the agent walks. If a rule wins there, the rule is what won.

Two live patterns

Authority is done correctly in encounters.py and wrongly in handlers.py. A charter does not invent a pattern here. It says which of two real ones to copy, which is most retrofits.

A working affordance

queries.update_log_payload() and delete_log_from() exist, work, and are called by /v1. A function that does the forbidden thing outranks a rule forbidding it.

A comment that lies

handlers.py opens with "every roll below goes through tarrasque.domain.rng". It does not. docs/ARCHITECTURE.md describes a repository layer the service never grew. Both outrank anything you write.

The call I made building this

I seeded four traps and left the newest layer outnumbered on purpose, because a rule the surrounding code already demonstrates measures nothing. That choice makes the effect visible. It also makes it larger than yours will be, and §4 says so again where it matters.

The sentence to carry into the next section

Every agent pull request measures your repository. It does not deliver a verdict on the agent. What comes back in fourteen minutes is a hotspot report.

Mixing a refuse-on-violation security rule with a naming preference, as equal-weight bullets, teaches everyone to read every line at the strongest weight. The cardinal sin, said once

An aspirational rule teaches the agent to lie. Write "all I/O here is async" over a 90%-synchronous service and one of two things happens. Either the agent discounts it and matches the code, or it obeys and the next run reads that new code as evidence. The rule has then bootstrapped its own contradiction into the imitation surface. Check the files on disk the day you write the rule, not the wiki.

The test for any line you are about to add

Can you name the specific thing that went wrong without it? If not, you are writing a wish. Wishes are free to add and impossible to remove, which is the combination that produces a charter nobody reads.

The family test, run backwards

Remove the thing and ask what changed. If the agent can do less, it was a capability. If it can do more, it was a constraint on the wrong ladder. Every capability carries four attributes: trigger, rung, grant, return.

Four rungs, from a macro to a process

Four questions place it, and you stop at the first that decides. Who notices the need? A human means a command. Does the work belong in another window? That is a sub-agent, the only rung that hands context back. Does it need a process wall? That is MCP. Otherwise it is a skill, which is where most of them belong and where almost nobody puts them.

What we install, and why each sits where it does

A rule bounds one move; a skill walks a job. Catch yourself writing a rule containing the word then and you are writing a sequence. Step 7 is a bundled script: reach for one of those before you reach for a server.

The MCP server we are about to delete

One tool, your language, no credentials, no other client. That is a script in a skill, and it costs one line where the server costs a full schema every turn, forever. I have written this server twice and deleted it twice.

The grant · permissions are the mechanism, intent is what you meant

A permission rule answers one question: may this string run? Yours is different: is this work permitted? The gap between them is where accidental grants live. So point the list at make targets, because a target is a unit of intent somebody decided on.

The predicate, written once, mounted four times

Two constraints are why the same forty lines run anywhere. It imports nothing from the project, and it never opens a file. Sources arrive as strings, so the same rules run over a diff, a staged tool call, or a payload from another machine.

Every refusal names its escape, and then you count the markers. A spike in exemptions says the rule is wrong, not that the agents are.

Mount one · the hook that refuses inside the turn

Where the feedback lands decides whether the loop converges. Caught inside the turn, the agent reads one error line and patches it. Caught afterwards, the tool has already reported "wrote the file", so the repair loop runs open. I have watched the same rule and model converge in zero repairs at the hook and never converge after it.

Probe · lever 4 against lever 2 · one minute

Make the request lever 2 talked you out of in §3, and push it the same way:

$ make lever N=4
→ "Add `import random` to tarrasque/api/encounters.py and roll a d20 with it."

In §3 the agent cited the rule and then folded. Here it agrees with you, writes the edit, and the write does not land. Exit 2 returns the reason into the same turn, and the agent repairs itself without being asked. The gap between declining and being unable is the difference between lever 2 and lever 4. Neither replaces the other. The rule explains the cost, and the hook holds the line at three in the morning.

The hook is the cheapest mechanical rung, and the only one inside its own blast radius

.claude/hooks/charter_gate.py is a file, and the agent has an edit tool. Nothing sits between those two facts except the deny rule you wrote five minutes ago. This is not about a scheming model: a careless human, a bad merge, or an instruction hidden in a page the agent fetched all reach the same file. Never ask whether it would. Ask what at this layer can.

Mount two · the Stop hook that verifies from the tree

The second hook verifies from the tree, never from the agent's report of the tree. That has a limit, and it is the hole this workshop cannot close: a gate holds until the subject can rewrite the verifier. The missing rung is a rule that a test change is not self-approving.

Mount three · the reviewer, for the rule no predicate holds

A gate enforces only the decidable shadow of a rule. The predicate sees that you read character_id out of the body. It cannot see that a player rolling their own death save is fine while rolling someone else's is the incident. Marking that none is honest; pretending a gate covers it is not.

Do not delete the rules you cannot enforce. Those lines look like decoration, and they are where the expensive failures live, precisely because no gate is watching them.

Pick the cheapest altitude that holds

Start at prose, where most rules stay. Promote on evidence rather than fear: a rule earns a check after prose fails, and a gate after the failure reaches production. Both are facts you can point at. The ceiling
1:127 minutes · where we stop, on purpose

Which rules have earned the next rung, and why we are not taking it

Everything you installed today is a file in a repository and a commit you can revert. Above that line, enforcement lives somewhere reconfiguring the agent cannot reach. Naming which of your rules belongs up there is this workshop. Putting it there is not.

make promote

Everything you installed is a file you can revert. Enforcement sometimes has to move where reconfiguring the agent cannot reach: a tool that refuses internally, a stage gate, CI. At that point we name it, write it down, and stop.

Three tests, and the third kills most candidates

A rule earns a mechanical rung only when all three hold. Consequential: being wrong costs something, silently. Recurrent: more than one person has broken it, more than once. Decidable: a machine can settle it. "The control check is the right one" is not decidable, and promotion will not make it so.

Nothing earned a promotion today, and that is the correct answer. Every rule failed exactly once, and once is not recurrence. The report is a ledger rather than a verdict, and its honest reading is "come back in a quarter". Promotion also costs engineering time on every future change, and almost nobody demotes a rule, so charters only grow.

What we built
1:197 minutes · the whole thing, in three pictures

Four levers, and exactly where each one intervenes

Every lever you applied sits at a different moment of a single turn. The harness reads two of them before it calls the model at all. One changes what the model may reach for. One refuses things after the model has decided and before they reach disk. Seeing when each fires is what makes the ladder stop being a metaphor.

One turn, with the charter installed

The charter is read, never executed: the harness runs, and the harness is not one of the layers. The gate fires between the model's decision and the disk, so the agent fixes its own mistake inside the same turn. The arrow that carries the most is the one going back up.

The same turn without any of it

And where the two rungs above would sit

Two mounts sit inside the charter and two above it. The line runs between the hook and the tool: a hook is charter content, mechanical, inside the blast radius of what it enforces. A tool that refuses internally is a different process saying no.

The same four levers, in any agent

We used Claude Code's file names because a workshop has to pick one tool's. None of the design is Claude-only. The levers are the concepts, and every agent has somewhere to put them.

One substitution in that table is lossy, and it is worth naming. A host with no tool-call hook cannot refuse a write inside the turn. You fall back to a pre-commit gate, which answers after the agent has moved on. Same rule, later feedback, and §6 is what that costs you.

The other risk is drift. Adopt a second agent and the same charter becomes two slightly different copies, then four. Some of this is converging: AGENTS.md and agent skills are becoming common ground. But coverage is partial, not every provider implements them, and nothing standard reaches the check layer yet. Until that changes you either maintain each host's copy by hand, or compile them from one source with a tool like Keystone. Either way the discipline is the same: pick one canonical file, and treat every projection as build output.

A fixed budget, a deletion day, and your own repository

Nothing in the ordinary operation of a team ever removes a charter rule. Without a hard constraint the charter only grows, until it stops working on a day nobody can name.

The budget is one line at the top of the file

That header turns every addition into a comparison. The question stops being is this rule good, because every rule is good. It becomes is this better than the weakest rule in the charter, which has an answer. Reach for promotion first: it is the only move where the charter gets shorter and the constraint gets stronger.

Deletion day

One afternoon a year, asking each rule when did this last do anything rather than is this still a good idea. A rule that has never blocked anything is either second nature or dead, and the two look identical until you have the numbers. Additions happen on their own; deletion needs a name and a date on it.

  6. §6–7 One or two rules that have earned the next rung, plus your budget, and whose name is on deletion day.
What today was not

Today was not a measurement. n is one per person per cell, one model, one seed repository, one rule family, and I designed those rules so the effect would show. Do not quote any of it as a rate. What you have is an instrument, in a repository you keep, pointed at a claim you can test on your own codebase. That is where I have no stake in how it comes out.

Where to start on an existing charter

Do not rewrite it. Go through it once and put a date and a cause on every line you can. The lines where you cannot are the answer: some are load-bearing and undocumented, the rest are the ones to delete first. That hour is usually the most informative anyone has spent on the file.
