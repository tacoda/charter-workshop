The claim
0:006 minutes

The charter alone moves the band. That is the claim, and it is falsifiable.

Same agent, same model, same laptop, same ticket. Nothing changes but files in the repository. By 1:10 you will have a matrix that says how far that got you on a codebase you did not write — including, possibly, that it got you nowhere. The instrument is in the repo precisely so the answer can come out against me.

CLAUDE.md .claude/ .mcp.json and nothing else

The objection, first

A charter written in advance is a list of guesses. That is true, it is the strongest argument against everything on this page, and I want it said out loud before we start rather than raised at 1:20.

The best practices you would put in a charter on day one are the ones the model already follows. The rules that matter are the ones your codebase taught you, and on day one you do not know them yet. So the honest way to build a charter is to start with nothing and add a rule only after something has gone wrong — which usually takes a year of bad days.

We do not have a year. We have ninety minutes, and the resolution is this: wrapping an existing application is not authoring in advance. The first run is the incident. The agent manufactures the evidence on demand, and every rule you write today will point at a diff you watched it produce twenty minutes earlier.

Where we stop

Everything in CLAUDE.md, .claude/ and .mcp.json is in scope — including the mechanical parts. A hook is charter content: it is a file in the repo, it is reviewed in the same diff as the rule it enforces, and it is the only mechanical enforcement the agent could delete. A tool grant is charter content. A sub-agent's refusal scope is charter content.

The moment enforcement has to move somewhere that reconfiguring the agent cannot reach — a tool that refuses internally, a stage gate, a judge node, CI — we name it, write it on the promotion report, and stop. That is the next rung up and it is a different workshop. §7 draws the line and §8 shows you the whole ladder in one picture.

Three eras deep, and they disagree with each other

tarrasque runs a tabletop play session: it rolls the dice, tracks the turn order, holds the condition timers, and writes an append-only log the table can read back. It is not a toy, and it is not clean. It is the shape of a repository you would actually be handed.

The same job, twice, eleven lines apart

Both of those are in the repository right now. Both pass the test suite. One is eleven hundred lines of precedent and the other is one file. An agent asked to add an endpoint reads the repository and writes the eleven-hundred-and-first line, because the code is a louder signal than any paragraph you can put above it.

Four traps, and why each one is there

Opposed

Seeding and provenance and append-only each have a working implementation in the repo that does the wrong thing, and no correct exemplar on the path the agent will walk. If a rule wins here, the rule is what won.

Two live patterns

Authority is done correctly in encounters.py and incorrectly in handlers.py. The charter's job is not to invent a pattern; it is to say which of two real ones to copy. That is most retrofits.

A working affordance

queries.update_log_payload() and delete_log_from() exist, work, and are called by /v1. A function that does the forbidden thing is louder than a rule forbidding it.

A comment that lies

handlers.py opens with "every roll below goes through tarrasque.domain.rng". It does not. docs/ARCHITECTURE.md describes a repository layer the service never grew. Both outrank anything you write.

Staying portable · Keystone

Everything shown today uses Claude Code's file names because a workshop has to pick one tool's. Keystone is the provider-agnostic version of the same discipline: you author under .charter/ in typed primitives, and keystone project compiles them down to .claude/, .cursor/rules/*.mdc, or a pointer block in AGENTS.md. The rule that makes it work is that the projected files are build output — editing .claude/ in a Keystone repo is editing a compiled artifact. §8 maps every primitive we install today onto its Keystone kind.

The sentence to carry into the next section

Every agent PR is a measurement of your repository, not a verdict on the agent. What comes back in fourteen minutes is a hotspot report.

What it reads
0:2612 minutes · levers 1 and 2

Describe the present tense, then name what binds

Two levers, one idea: everything the agent reads before it acts. The root file says what this codebase is. The rule files say which lines are load-bearing and what each one cost. Neither can refuse anything, and both are still the cheapest thing you own.

CLAUDE.md .claude/rules/*.md

Lever 1 · the file read on every turn

CLAUDE.md fires on everything. A path-scoped rule fires when its path is touched; a skill fires when it triggers; a hook fires on its event. This one is in the window when the agent picks a variable name. That reach is why it is powerful and why a wrong line in it is expensive: the mistake fires on every token.

Eight sections, 800–1500 words, and none of them is "our engineering philosophy". A 2,000-word file is read. A 12,000-word file is skimmed, and by the eight-hundredth token the agent is acting as though the rest does not exist — which is the correct response, because the rest is wallpaper.

Three things earn their place there. The era paragraph, because without it "follow existing patterns" resolves to the god file. The mixed-codebase rule — match the layer you are in — because without it an agent handed an honest description of a contradictory repo will either drag the new pattern into old files or spread the old one, and both are failures of the same missing sentence. And the admission that a document in the repo is wrong, because you cannot always delete the lie, and naming it is the next best thing.

Lever 2 · three tiers, and four parts per rule

A file that mixes a refuse-on-violation security rule with a naming preference, presented as equal-weight bullets, teaches everyone to read every line at the strongest weight. The vocabulary is mine, not the tool's — a stock harness reads a rule file as undifferentiated text — and it has earned its keep because the marker forces the author to decide the strength before shipping the line.

1 · the rule

Behavioural and specific to this system. "Every die comes from an Rng stream" is a rule. "Be careful with randomness" is a mood.

2 · the altitude

gate, check, human, or none. Writing it down forces the question does anything enforce this, which is uncomfortable about a third of the time.

3 · the date and the link

So it can be looked up, and so §7's review is possible at all. Also tells a reader whether the rule is from a world that still exists.

4 · the damage

In the units the business uses. Eleven sessions unverifiable wins an argument under deadline pressure. It caused a bug loses it.

Your turn · six minutes
  1. 1 · write one Open .claude/rules/authority.md — no, open a scratch file. Write one rule with all four parts, for the failure your own baseline run produced fifteen minutes ago. Not a rule you believe in. The one you just watched cost you.
  2. 2 · pick its tier IRON only if a violation costs something the team would refuse to pay, ever. Most rules are GOLDEN, and a GOLDEN rule that is silent on its exception collapses into whichever tier the reader feels like.
  3. 3 · apply the rest make lever N=1 then make lever N=2 — lands the full CLAUDE.md and four rule files. Read the one that covers the failure you just wrote up and see whether yours says it better.
  4. 4 · check make levers — confirms what is installed.
The cardinal sin, said once

An aspirational rule teaches the agent to lie. Write "all I/O here is async" over a 90%-synchronous service and one of two things happens. Either the agent discounts the rule and matches the code — annoying, recoverable — or it obeys, the new code lands, the next run reads that code as evidence, and the rule has bootstrapped its own contradiction into the imitation surface. Then the codebase teaches two truths to every future run. Check the files on disk the day you write the rule, not the wiki.

Staying portable · Keystone

Both of these are the guide primitive: proactive input, loaded ambient, applied by judgement, glob-scoped so it activates on the files actually touched. In Keystone you write one .charter/guides/dice.md with kind: guide and a globs: field in its frontmatter; projection emits a rule shim under .claude/rules/, a .cursor/rules/dice.mdc with the globs mirrored verbatim, and a pointer block in AGENTS.md for everything else. One canonical file, every host's dialect. The tier marker travels in the body, because it is a team convention rather than a tool feature — in either world.

The test for any line you are about to add

Can you name the specific thing that went wrong without it? If not, you are writing a wish. Wishes are free to add and impossible to remove, which is the exact combination that produces a charter nobody reads.

What it can do
0:4612 minutes · lever 3

The other half of the charter, and the half nobody designs

A charter is easy to read as a list of prohibitions. Most of a working one is not. It is the set of things the agent can do at all — and teams install those without designing them, because installing feels free. It is not free.

command skill sub-agent MCP server plugin grant

The family test, run backwards

Remove the thing and ask what changed. If the agent can do less, it was a capability. If the agent can do more, it was a constraint and it is on the wrong ladder — and writing a constraint as a capability is how it stops being obeyed. A skill that says always run the formatter reads like a capability and behaves like a rule; it belongs in §3, at whatever tier §3 chose.

Every capability carries four attributes. Three have obvious counterparts on the constraint side. The fourth does not exist there at all, because a constraint never has to be found.

four attributes · collapse any two and you have installed a file, not a design
attributethe question it answerswhere it is written
triggerwho invokes this, and how do they find it?the description line
rungwhat carries it, and how much can the model reinterpret?which directory it lives in
grantwhat may it touch while it runs?allowed-tools / tools
returnwhat crosses back, and what stays behind?the body, stated explicitly

Four rungs, from a macro to a process

Four questions place it, and you stop at the first one that decides. Who notices the need? A human, at a moment of their choosing, means a command. Does the work belong in another window? Bulk reading, wide search, anything whose byproduct is bigger than its answer, means a sub-agent — the only rung that hands context back. Does it need a process wall? Several clients, an interactive sign-in, a vendor's server, a versioned contract: that is MCP. Repeatability is not on that list, because a bundled script gives you that for nothing. Otherwise it is a skill.

What we install, and why each sits where it does

Three lines there do the work. $1 makes the file a function rather than a note. The ! prefix collects the evidence before the model starts, so it cannot forget to look. And disable-model-invocation takes the description out of the standing bill — the right default for anything a human always initiates.

A rule bounds one move; a skill walks a job. The test is mechanical: if you catch yourself writing a rule with the word then in it, you are writing a sequence, and a sequence does not belong in the rules directory. That is why endpoints in this repo kept arriving half-finished — the handler landed and the log entry did not, because nothing told the agent how many moves were in the job.

Note step 7. check_route.py is a bundled script: no standing cost, no schema, no process, and the same answer every time. It is the cheapest determinism on the ladder, and it is what you reach for before you reach for a server.

Two lines carry that file. The tools: line is a grant, and a grant left off is a grant inherited by accident — the sub-agent silently holds everything the parent held, including the write tool. The return block is the interface: a sub-agent with an unstated return shape returns prose, and prose is exactly what you were trying to keep out of the parent's window.

The MCP server we are about to delete

One tool. Your language. No credentials. No network. No other client. That is a script in a skill, and it costs one line where the server costs a full schema in every turn of every session anyone opens in this repository, forever. I have written this server twice and deleted it twice.

Keep MCP for the five cases that earn it: several clients need the same access, sign-in is an interactive flow the model must not handle, the surface is broad enough that typed discovery pays for itself, a vendor already ships one, or other teams need a versioned contract. And remember what comes back through the wall is text landing next to your instructions — a tool that reaches content other people wrote is returning an untrusted string into a context that treats strings as instructions.

The grant · permissions are the mechanism, intent is what you meant

A permission rule answers one question: may this string run? The question you actually have is different: is this work permitted? Every allowlist is a lossy translation between the two, and the loss is where accidental grants live. The repair is to point the list at make targets, because a target is a unit of intent somebody decided on, and adding one is a reviewed change to the Makefile.

Your turn · five minutes · no model call needed
  1. 1 · apply make lever N=3 — lands the command, the skill, the sub-agent, an .mcp.json, and a deliberately bad .claude/settings.json.
  2. 2 · audit it make grants — it finds seven accidental grants in eight lines. Read them before you look at the answer.
  3. 3 · the one that matters Find the rule that lets the agent edit .claude/. Fix that one by hand.
  4. 4 · delete rm .mcp.json. Say out loud why.

Both ends of the dial fail, and they fail asymmetrically. A loose list fails once, loudly, on the day an ambiguous prompt meets a general tool. A tight list fails quietly and continuously, by generating so many prompts that somebody turns the whole thing off — and the failure mode of over-restriction is under-restriction, arriving later and unlogged. The fix for both is fewer things to permit.

Read the allow block as a sentence: this agent may run the project's own checks, read anything in the repo, and write in the two places new work belongs. That sentence is the design. The list is just how you say it to a matcher.

Staying portable · Keystone

Four of these map straight across. A command is a command; a skill is a skill (framework authors usually reach for playbook, which wraps one and names the halt conditions between steps); a sub-agent is an agent; an MCP declaration is a tool with transport: mcp — alongside cli, http and plugin, which is the point, because the transport stops being the thing you think about. The permission list is a posture, and projection writes it out as this host's settings.json. Every one declares kind, id and description in frontmatter, and keystone verify fails at install time if a playbook names a command the cascade does not carry.

Twelve anti-patterns, and only two are about the mechanism

Four are trigger failures — the unread skill, the kitchen sink, the twin, the rule in a skill's clothing. Three are return failures — the API mirror, the chatty return, the blind parent. One is a grant failure: the sub-agent with no tools: line. Capability work is mostly interface work, done in one line of frontmatter and one paragraph about what comes back.

What refuses it
0:5812 minutes · lever 4, then run C

Two verdict sources, one implementation

A check can be settled by running code or by reading. Both belong in the charter, they answer different questions, and the column that has been printing ? since 0:20 needs the second kind.

PreToolUse hook Stop hook reviewer sub-agent

The predicate, written once, mounted four times

tools/charter_check.py takes {files: [{filename, source}]} and returns a verdict. Two constraints on it are deliberate and load-bearing, and they are the whole reason the same forty lines can go anywhere.

It imports nothing from the project. The moment it imports tarrasque it can only run where tarrasque is installed, and every mount outside the repo stops working. It never opens a file. Sources arrive as strings, so the same rules run over a diff, over a staged tool call, or over a payload from a machine with no shared filesystem.

Every refusal names its escape, and then you count the markers. A spike in exemptions says the rule is wrong, not that the agents are. A rule with no escape hatch does not get obeyed; it gets routed around, by a helper module your glob does not cover.

Mount one · the hook that refuses inside the turn

Where the feedback lands decides whether the loop converges. When the same violation is caught by a hook inside the turn, the agent reads one error line and patches it, and the next turn starts clean. When it is caught after the loop, by a gate walking the tree, the tool has already reported "wrote the file" — the agent never learned within the turn that its fix did not work, and the repair loop runs open-loop. I have watched the same rule, the same violation and the same model converge in zero repairs at the hook and fail to converge at all after the loop.

The hook is the cheapest mechanical rung, and the only one inside its own blast radius

.claude/hooks/charter_gate.py is a file, and the agent has an edit tool. Nothing sits between those two facts except the deny rule you wrote five minutes ago. This is not about a scheming model: a careless human, a bad merge, or an instruction hidden in a page the agent fetched all reach the same file. Never ask whether it would. Ask what at this layer can.

Mount two · the Stop hook that verifies from the tree

The second hook runs make verify at the end of the turn, over what is actually on disk — never over the agent's report of what is on disk. Verify from the tree, not from the transcript. It is the last moment the feedback is still cheap.

That principle has a limit worth naming, because it is the hole this workshop cannot close. A gate that re-runs the test suite holds until the subject can rewrite the verifier. The missing rung is not a seventh checker; it is a rule that a test change is not self-approving. Our C7 lives in the scorer rather than the gate for exactly that reason — it needs the diff, not the source — and .claude/settings.json puts the characterization file behind ask.

Mount three · the reviewer, for the rule no predicate holds

A gate enforces only the decidable shadow of a rule. The predicate can see that you read character_id out of the body. It cannot see that a dungeon master should be able to roll for an unconscious player's character, that a charmed character is controlled by whoever charmed them for the duration, or that a player rolling their own death save is fine while rolling someone else's is the incident that put the rule in the file. Those are judgements, and marking them none is honest where pretending a gate covers them is not.

Do not delete the rules you cannot enforce. A tidy-minded instinct says to cut every line no gate backs, because those lines look like decoration. The unenforceable lines are where the expensive failures live, precisely because no gate is watching them.

Staying portable · Keystone

Both mounts are the sensor primitive — reactive feedback, applied by execution, subscribing to a moment via on:. There is no separate hook kind: a computational sensor declares run: and its exit status is the verdict; an inferential sensor declares returns: and is dispatched as an agent review. Same subscription model, two verdict sources, and the subscription lives in the canonical file — so you cannot quietly unhook a gate without the change showing up in the same diff as the rule. on: takes host phases like PreToolUse and Stop, or any signal your project defines and fires itself.

Pick the cheapest altitude that holds

Start at prose; most rules never need to leave. Promote on evidence, not fear: a rule earns a check after prose fails, and a gate after the failure reaches production. Both are facts you can point at. And never gate what has legitimate exceptions — a refusal people override weekly teaches everyone that refusals are negotiable, which damages the gates that are not.

The ceiling
1:108 minutes · where we stop, on purpose

Which rules have earned the next rung — and why we are not taking it

Everything you installed today is a file in a repository and a commit you can revert. Above that line, enforcement lives somewhere reconfiguring the agent cannot reach. Naming which of your rules belongs up there is this workshop. Putting it there is not.

make promote

Three tests, and the third kills most candidates

A rule earns a mechanical rung only if it is consequential — being wrong costs something, and costs it silently; recurrent — it has been broken more than once, by different people; and decidable — a machine can settle it. "No unseeded roll outside rng.py" is a predicate over a syntax tree. "The control check is the right one" is not, and no amount of promotion will make it one.

Nothing in that table earned a promotion today, and that is the correct answer. Every rule failed exactly once, in the bare run, and once is not recurrence. A workshop produces one data point per rule; a year of your own captured runs produces the number that decides. Which is the point: the report is not a verdict, it is a ledger you keep adding to, and the honest reading of it after ninety minutes is "come back in a quarter".

Two judgement calls in that table are worth naming. A rule with a handful of blocks stays, because the metric is expected damage, not frequency — one unverifiable session dwarfs a hundred scope warnings. And a rule with a hundred and forty-seven blocks is not a success story: something upstream keeps producing changes that violate it, and the rule is absorbing a problem instead of solving it.

The two rungs above, in one table, and then we stop

Both of the verdict sources you built today exist at every altitude. That symmetry is the only thing you need from the rungs above: the same rule, the same two kinds of check, mounted where a different actor owns the enforcement.

A DAG is an acyclic pipeline — fixed steps, edges forward, runs to completion. A loop is cyclic: act, check, route, back to act, until a bound fires. A factory is a topology of governed steps with humans at named touchpoints. Every one of them hangs the same two kinds of check off its edges. That is the whole map, and it is as far as we go.

Two reasons to stop here rather than keep climbing

The first is honest scope: the claim this workshop can actually demonstrate in ninety minutes is a claim about the repo layer, and a session that reaches upward loses the one thing it could prove. The second is that promotion costs engineering time and adds friction to every future change. Most rules never need to leave prose. Almost nobody demotes a rule, which is why charters only grow — so before you promote anything, check whether a gate whose rule has become second nature could come back down instead.

Write it down, then stop

Section 6 of HITLIST.md takes one or two rules, no more, with what each costs when it is broken and how many times it has been broken by different people. Promoting it is next week's problem and somebody else's workshop. Writing down that it has been earned is this week's.

A fixed budget, a deletion day, and your own repository

Nothing in the ordinary operation of a team ever removes a charter rule. Without a hard constraint the charter only grows, until it stops working on a day nobody can name.

40 lines adding requires removing deletion day

The budget is one line at the top of the file

It turns every addition into a comparison. The question stops being is this rule good — every rule is good — and becomes is this rule better than the weakest rule in the charter, which is a question with an answer. Three ways to make room: merge two rules about the same thing, promote one out of prose into a gate and delete the prose, or delete one that has not fired in a year.

Promotion is the move to reach for first, because it is the only one where the charter gets shorter and the constraint gets stronger.

Deletion day

One afternoon a year, with the audit trail open, asking for each rule when did this last do anything rather than is this still a good idea. It is why a trail records passes as well as blocks: a rule that has never blocked anything is either second nature or dead, and both look identical from outside until you have the numbers. Additions happen on their own, because adding a rule is how a team shows the incident mattered. Deletion has no such motivation behind it. Put a name and a date on it, or accept that the charter grows forever.

What today was not

It was not a measurement. n is one per person per cell, one model, one seed repository, one rule family, and I designed those rules so the effect would be visible. Nothing here has statistical significance and none of it should be quoted as a rate. What it is: an instrument, in a repository you keep, pointed at a claim you can now test on your own codebase — where the answer actually matters and where I have no stake in how it comes out.

Where to start on an existing charter

Do not rewrite it. Go through it once and put a date and a cause on every line you can. The lines where you cannot are your answer: some are load-bearing and undocumented, and the rest are the ones to delete first. That exercise takes an hour and it is usually the most informative hour anyone has spent on the file.
